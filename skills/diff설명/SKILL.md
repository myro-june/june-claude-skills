현재 브랜치의 변경사항(diff)을 읽는 사람이 깊이 이해할 수 있는 **자체 포함 HTML 설명서**로 변환합니다.
Geoffrey Litt의 [explain-diff 프롬프트](https://gist.github.com/geoffreylitt/a29df1b5f9865506e8952488eac3d524)를 기반으로 하며,
PR 생성 게이트(`~/.claude/hooks/explain-diff-gate.py`)와 diff 범위·마커를 공유합니다.

**중요: 백그라운드 Agent를 스폰하지 말고 현재 컨텍스트에서 직접 실행한다.**

## Workflow

### Step 1: diff 범위 확인 (게이트와 동일한 기준 사용)

```bash
python3 ~/.claude/hooks/explain-diff-gate.py --info
```

반환 JSON의 `base`(기본 브랜치와의 merge-base), `files`(변경 파일 목록),
`suggested_html`(출력 경로)을 사용한다. `files`가 비어 있으면
"설명할 변경사항이 없습니다"라고 보고하고 종료한다.

인자로 특정 대상(브랜치, PR 번호, 파일 경로 등)이 주어지면 그 범위를 설명하되,
마커는 현재 워크트리 기준으로만 기록됨을 사용자에게 알린다.

### Step 2: 컨텍스트 수집

- `git diff <base>` — 전체 변경 내용 (워크트리 기준, untracked 파일은 직접 Read)
- `git log <base>..HEAD --oneline` — 커밋 이력 (있는 경우)
- 변경 파일과 맞닿은 주변 코드를 Read하여 "변경 전 시스템"을 파악한다.
  Background 섹션의 품질은 이 단계에 달려 있다.

### Step 3: HTML 설명서 생성

`suggested_html` 경로에 **단일 자체 포함 HTML 파일**을 작성한다.

**문서 구조 (4섹션 + 목차):**

1. **Background(배경)** — 변경 전 시스템이 어떻게 동작했는지. 이 코드베이스를
   전혀 모르는 동료에게 말로 설명하듯 쓴다. 등장인물(도구·파일·개념)을 하나씩
   소개한 뒤에만 본론으로 들어간다.
2. **Intuition(직관)** — 이 변경의 핵심 아이디어. "무엇이 문제였나 → 왜 문제인가
   → 해결 아이디어 → 어떻게 구현했나" 순서의 스토리로 쓴다. 구체적 예시
   1개 이상과 다이어그램 필수. 예시 데이터가 흐르는 모습을 보여줄 것.
3. **Code(코드)** — 변경사항을 파일 순서가 아니라 **개념 단위로 그룹핑**해서
   안내한다. 각 그룹마다 대표 코드 조각을 인용하고 의도를 설명한다.
4. **Quiz(퀴즈)** — 중간 난이도 객관식 5문제. 클릭하면 정답/오답 피드백과
   해설이 나오는 인터랙티브 JS. **정답 위치는 문제마다 무작위로 분산**시킨다
   (전부 같은 번호 금지). 해설도 아래 "쉬운 설명 원칙"을 따른다.
   각 해설 끝에는 근거가 되는 본문 앵커로 점프하는 **`📍 본문에서 확인` 링크**
   (`<a class="jump" href="#앵커id">`)를 반드시 넣는다 — 클릭 시 부드러운
   스크롤 + 대상 문단이 **샛빨간 배경**(`#ff443a` 계열, 눈에 확 띄어야 함)으로
   2~3초 강하게 하이라이트(`.flash` 애니메이션)된 후 원상 복귀.
   **본문에 근거 문단이 없는 내용은 퀴즈로 내지 않는다** — 필요하면 근거를
   본문에 먼저 추가한 뒤 퀴즈를 만든다.

**쉬운 설명 원칙 (기본 모드 — 반드시 적용):**

- **핵심 용어·개념은 쉬운 말로 바꿔치기(삭제)하지 말고 원본 그대로 유지한다.**
  용어를 쓰되 첫 등장에서 괄호 한 줄 풀이(+가능하면 비유)를 붙이고, 이후에는
  용어만 자유롭게 쓴다. 예: "merge-base(두 브랜치가 갈라지기 시작한 지점의 커밋)",
  "PreToolUse 훅(Claude가 도구를 실행하기 직전에 끼어드는 검문소)".
  독자가 문서를 읽은 뒤 실제 코드·명령·로그에서 같은 용어를 만났을 때
  알아볼 수 있어야 한다. 풀이 없이 쓴 전문용어가 남아도 안 되고,
  용어를 피하려고 평문으로만 뭉개(용어 실종)도 안 된다.
- **풀이된 용어는 점선 밑줄로 표시한다** (`.term` 클래스,
  `border-bottom: 2px dotted` 스타일). "이 단어는 본문에서 정의된 용어"임을
  시각적으로 구분할 수 있게 한다.
- **개념마다 실생활 비유 또는 미니 예시를 하나 붙인다.**
  예: 게이트 = "공항 보안검색대 — 탑승권(설명서) 없으면 통과 불가",
  diff 내용 해시 = "책 내용으로 판단하지, 몇 쇄인지(커밋 번호)로 판단하지 않는다".
  **마크업 규약 (게이트가 개수를 센다 — 최소 5개):** 비유·예시는 본문 문장에
  녹이지 말고 `<div class="box">` 블록으로 감싸고 라벨을 붙인다.
  비유는 `<span class="lab">🔎 비유</span>`, 예시는 `.warnbox`를 함께 주고
  `<span class="lab">▶ 예시로 따라가기</span>`. 예시는 **구체적인 값으로**
  따라가게 쓴다 — "그룹 삭제 → fk=NULL → 12만원이 조회에서 빠짐"처럼
  숫자와 상태 변화가 보여야 하고, 원리 서술로 대체하지 않는다.
- **문장은 짧게, 한 문단은 3~4문장 이내.** 길어지면 문단을 쪼갠다.
- **코드 블록 위에는 "이 코드가 하는 일" 한 줄 요약**(`.code-lead` 클래스,
  게이트가 최소 3개를 센다)을 평문으로 먼저 쓴다.
  독자는 요약만 읽고 코드를 건너뛰어도 흐름을 잃지 않아야 한다.
  이 요약 줄은 문서에서 가장 평이해야 하는 자리이므로 **전문용어를 넣지
  않는다** — 용어 재사용은 요약 줄이 아니라 본문 문단에서 한다.
- **추상 → 구체 순서 금지, 구체 → 추상 순서로.** 예시를 먼저 보여주고
  일반 원리를 뒤에 정리한다.
- 인자에 `전문가`가 포함된 경우에만 이 원칙을 완화하고 간결한 전문가 문체를 쓴다.

**스타일 요구사항:**

- CSS/JS 전부 인라인, 외부 리소스 없음 (오프라인에서 열려야 함)
- 탭 없이 긴 단일 페이지 + 상단 목차(앵커 링크)
- 반응형(모바일에서도 읽힘), 다크 배경 무관하게 읽히는 자체 배경색 지정
- 다이어그램은 ASCII 아트 금지 — HTML/CSS(flexbox, border, 색 블록)로 그린다
- 코드 블록은 `<pre>` + `white-space: pre-wrap` (가로 스크롤 방지)
- 산문은 한국어, 코드·식별자·기술 용어는 원문 유지
- 문체는 명료하고 흐름이 자연스럽게 — 섹션 사이 전환 문장을 넣는다

### Step 4: 마커 기록 (게이트 통과용)

```bash
python3 ~/.claude/hooks/explain-diff-gate.py --mark --html <생성한 HTML 경로>
```

이 시점의 diff 내용 해시가 마커에 기록된다. 이후 변경사항이 더 생기면
게이트가 stale로 판정하므로, 추가 수정 후에는 이 스킬을 다시 실행해야 한다.

`--mark`는 기록 전에 **HTML 무결성 검사**를 자동 실행한다. 검사 항목:

| # | 항목 | 기준 |
|---|---|---|
| 1 | 퀴즈 개수 | 5문제 |
| 2 | `data-answer` | 숫자 + 보기 개수 범위 안 |
| 3 | 보기 | 문제당 2개 이상 |
| 4 | 점프 링크 `.jump` | 문제마다 1개 이상 |
| 5 | 내부 앵커 `#` | 대상 id가 문서에 존재 |
| 6 | 정답 위치 | 전부 같은 번호 금지 |
| 7 | `.flash` 하이라이트 | CSS 정의 + `classList.add('flash')` 둘 다 |
| 8 | `.term` 용어 풀이 | 1개 이상 |
| 9 | `.diagram` | 1개 이상 |
| 10 | `.box` 비유/예시 | 5개 이상 |
| 11 | `.code-lead` 코드 요약 | 3개 이상 |

⚠️ **이 표가 실제로 강제되는 유일한 지점이다.** 위 「쉬운 설명 원칙」·
「스타일 요구사항」 중 이 표에 없는 항목(문단 길이, 설명의 충실도, 구체→추상
순서 등)은 기계가 보지 못하므로 작성자가 지켜야 한다. 표에 있는 항목만
지키고 나머지를 빠뜨린 문서가 과거 2건(2026-08-10 / 08-12) 나갔다.

**불합격이면 마커를 기록하지 않으므로**, 출력된 오류 목록대로 HTML을 고친 뒤
다시 실행한다.
단독 검사: `python3 ~/.claude/hooks/explain-diff-gate.py --check-html <경로>`

### Step 5: 결과 안내

```bash
open <생성한 HTML 경로>
```

브라우저로 연 뒤, 사용자에게 다음을 한 줄씩 보고한다:
파일 경로 / 다룬 변경 파일 수 / 퀴즈 문항 수 / "이제 PR 생성 게이트를 통과할 수 있습니다".

## Rules

- 설명서는 diff를 나열하는 문서가 아니라 **가르치는 문서**다. "무엇이 바뀌었나"보다
  "왜, 어떤 개념으로 바뀌었나"에 지면을 쓴다.
- 퀴즈는 표면 암기가 아니라 이해를 검증한다 ("이 상황에서 어떻게 동작하는가" 유형).
- 산출물은 레포 밖(`~/.claude/explain-diff/<repo-slug>/`)에 저장된다 — 레포 안에
  두면 산출물 자체가 diff에 포함되어 게이트 해시가 계속 어긋난다. 경로를 임의로
  레포 안쪽으로 바꾸지 말 것.
- 게이트 우회(`SKIP_EXPLAIN=1`)는 사용자가 명시적으로 지시한 경우에만 사용한다.
