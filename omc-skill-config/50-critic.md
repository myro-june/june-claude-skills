### codex:critic 호출 패턴 (OMC custom — plugin 미제공)

`codex:critic`은 **OMC가 정의한 custom 호출**이다. codex-plugin-cc에는 critic command가 없으므로 OMC가 critic.md 주입 방식으로 별도 정의했다. (codex:review / codex:adversarial-review는 plugin 자체 native command — `51-codex-reviews.md` 참조)

**parent 세션에서 직접 Bash로 codex-companion.mjs `task` subcommand를 호출**한다. 우회 사유:

1. `omc ask codex --agent-prompt critic`은 critic.md YAML frontmatter(`---`)를 codex exec arg parser가 CLI 플래그로 오인하는 버그가 있어 사용 불가.

호출 절차:

1. critic 프롬프트 로드: `~/.claude/plugins/cache/omc/oh-my-claudecode/<최신 버전>/agents/critic.md` 를 Read하고 YAML frontmatter(첫 `---`~두 번째 `---`) 제거 (버전 디렉토리는 glob으로 탐색해 최신 선택 — 활성 런타임과 동일 사본. marketplaces 사본은 버전 드리프트 위험으로 사용 금지)

   - 명령 형식: `node "${CLAUDE_PLUGIN_ROOT}/scripts/codex-companion.mjs" task --fresh --write "<prompt>"`
   - `${CLAUDE_PLUGIN_ROOT}`가 unresolve되면 절대경로 사용: `/Users/june/.claude/plugins/marketplaces/openai-codex/plugins/codex/scripts/codex-companion.mjs` (allowlist 등록됨)

### 선제 환경 컨텍스트 주입 (MANDATORY)

**적용 대상**: autopilot Phase 0/1, ralplan, team ralph **+ autopilot Phase 4(Stage 0·1·2)** — **프롬프트 주입이 가능한 리뷰어 전부**(`54-phase4-registry.md` 「프롬프트 주입」=가능 인 행). Deadlock 조기 감지(사후 대응)의 선제 버전으로, 반복 지적이 생기기 전에 원천 차단한다.

Critic·리뷰어 루프 시작 전(1라운드 호출 직전) 다음 **세** 소스에서 수집한다:

1. **현재 세션 사용자 발언** — 환경 제약(예: 샌드박스 localhost 차단, 운영 DB 미가동, 외부 API mock 사용)과 이미 내려진 정책 결정(위험 수용 방식 등)
2. **`.omc/deferred/` 기존 기록** — 이전 실행에서 "사용자 dismiss" 출처로 기록된 finding (**세션 간 승계** — dismiss 결정이 다음 실행에서 재발견되는 것 방지)
3. **이번 실행의 이월 기록 전체 (MANDATORY)** — 산출물별 이월 저장소를 **전건** 읽는다: ralplan `ADR Follow-ups` · autopilot Phase 4 `.omc/deferred/<날짜>-<작업>.md` **전체 행** · deep-interview 이월 항목. **"사용자 dismiss" 출처만이 아니라 오케스트레이터가 scope 판정으로 이월한 것도 포함한다.**
4. **계획의 Open Question 전건 (MANDATORY)** — ralplan 산출물의 `OQ` 표 · plan 본문의 미결 항목. **OQ는 "미결"이지 "무시해도 되는 것"이 아니다** — 해소 시점이 계획에 적혀 있으면(예: *"P5 이전 확정 권장"*) 그 시점에 닫아야 하고, 안 닫으면 리뷰어가 **차단 등급으로** 재발견한다.
   - **왜 필요한가**: 이월은 파일에 기록되지만 **리뷰어는 그 파일을 읽지 않는다.** codex critic 은 `task --fresh` 라 라운드 간 기억이 0이고, 다른 fresh 호출 리뷰어도 같다. 그래서 **한 번 판단이 끝난 항목을 매 라운드 다시 발견**한다.
   - **실사례 2건**: ⓐ 2026-08-05 ralplan — codex critic 이 동일 finding 을 10회 반복해 15라운드 한도를 소진(본 파일 Deadlock 절 배경). 그때 대응은 **탐지**(Deadlock 에스컬레이션) 추가였고 **예방**은 붙이지 않았다. ⓑ 2026-08-07~08 autopilot Phase 4 — round 2 에 이월한 항목을 round 10 에 `codex:adversarial-review` 가 동일 요지·동일 근거로 재지적(같은 라운드에 이월 목록을 프롬프트로 받은 codex:critic·ocr 은 *"deferred items are explicitly recorded and not re-litigated here"* 로 명시 존중했다 — **주입 유무가 결과를 갈랐다**).

수집분이 1건 이상이면 **양 Critic(OMC + codex) 호출 프롬프트의 리뷰 대상 앞에 "환경 컨텍스트" 블록**을 붙인다 (fresh 호출인 codex:critic에 특히 필수):

```
## 환경 컨텍스트 (오케스트레이터 제공 — 판정에 반영할 것)
- <invariant/결정 요지> (출처: 사용자 발언 / deferred YYYY-MM-DD)
이 항목들을 전제로 한 지적은 새 근거가 없는 한 차단 사유로 삼지 않는다.
```

- 블록은 **매 라운드 유지**한다. 루프 중 dismiss가 발생하면 기존 "조정 이력 주입"(Deadlock 옵션 A) 블록과 병합해 하나로 유지.
- **상시 표준 항목 (MANDATORY — 2026-08-21 신설)**: 리뷰 과정에서 **코드 실행이 예상되는 리뷰어**(codex 계열 전부 · 테스트 실행을 요구받는 슬롯)에게는 수집분과 무관하게 아래 1줄을 블록에 **항상** 포함한다:
  > - codex 샌드박스는 포트 바인드(`listen EPERM`)·vitest temp 생성(EPERM)·외부 DB 접속을 차단한다 — 테스트 실행 실패는 환경 아티팩트이지 코드 결함이 아니며, 실행 증거는 오케스트레이터의 로컬 실측이 공급한다 (출처: 상시 표준)
  근거: 2026-08-20~21 STAT-590 Phase 4 — codex:critic·adversarial 이 EPERM 을 매 라운드 Minor 로 보고했고, 오케스트레이터가 매번 "환경 탓·로컬 877 passed" 판정을 반복했다. 표준 항목 1줄이 그 왕복을 없앤다.
- 수집 0건이면: 상시 표준 항목 해당 리뷰어에는 **표준 항목만으로 블록을 구성**하고, 그 외 리뷰어는 블록 생략(빈 블록 금지). 추측성 invariant 날조 금지 — 상시 표준·사용자 발언·deferred 기록에 실재하는 것만.
- 선제 주입이 있어도 Deadlock 조기 감지는 그대로 수행한다 (독립 동작).

#### 🔴 주입 블록은 **파생**이어야 한다 — 큐레이션본 재사용 금지 (MANDATORY)

**anti-pattern**: ❌ 앞선 라운드/Stage 를 위해 **손으로 고른** 컨텍스트 파일을 다음 라운드·다른 Stage 에 **그대로 재사용**한다.

**왜 금지인가**: 큐레이션은 **그 라운드의 축에 맞춰** 만들어진다. 축이 바뀌면(Stage 2 → Stage 1, 리뷰어 종류 변경, 스코프 이동) 그 축에 없던 항목이 **조용히 빠진다**. 그리고 **큐레이션의 손실은 아무 흔적도 남기지 않는다** — 빠진 항목은 표시가 없고, 리뷰어가 그걸 짚을 때까지 모른다.

**규칙만으로 안 되는 이유는 인센티브다**: 2000줄짜리 이월 파일에서 다시 뽑는 것보다 이미 있는 파일을 재사용하는 게 훨씬 싸다. 그래서 **"조심하자"가 아니라 뽑는 쪽을 싸게 만든다.**

- [ ] **이월 항목 수 ≥ 저장소 실측 항목 수**인가? 적으면 **무엇이 빠졌는지** 대고 진행하라
- [ ] **OQ 표 행 수 > 0인데 주입한 OQ가 0건**인가? → 즉시 위반. OQ 는 별도 소스라 이월 목록에 안 들어 있다
- [ ] 이 블록이 **직전 라운드용으로 만든 파일과 동일 파일**인가? 동일하면 축이 바뀌지 않았음을 근거로 대라

**도구화 권장**: 프로젝트에 추출 스크립트를 두면 파생이 재사용보다 싸진다. 참고 구현 — `.omc/tools/build-reviewer-context.mjs`(eagleray): 이월 섹션과 OQ 표를 **원문 그대로** 잘라 붙이고 `--count-only` 로 수량을 낸다. **요약하지 않는다 — 요약이 곧 큐레이션이고 큐레이션이 곧 손실이다.**

위 대조 항목 *"이월 항목 수 ≥ 저장소 실측 항목 수인가"* 는 두 수치가 **다른 출처**일 때만 성립한다. 그런데 도구를 도입하면 **둘 다 그 도구가 낸다** — 필터가 절반을 버려도 「추출 수량」과 「실측 수량」이 사이좋게 같이 줄어 대조가 통과한다. **필터의 사각지대는 필터의 출력으로 검사할 수 없다.**

**실사고**: eagleray 추출기가 `## `/`### ` 제목이 이월 키워드(`이월|판정|사용자 결정|…`)에 걸릴 때만 그 절을 실었다. 그런데 **리뷰 기록의 소제목은 finding 을 서술**하지 이월을 서술하지 않는다 — `## 슬롯3 codex:critic — REVISE` · `### [MAJOR-1] (신규) …` · `### test-engineer C-1 (Critical)` · `## Stage 2 재실행 #4` 는 어느 키워드에도 안 걸린다. 결과: **라운드 13 블록 전체 + Stage 2 9슬롯 리뷰 기록 전부**가 5개 라운드에 걸쳐 리뷰어에게 전달되지 않았다(커버리지 **35%**). 발견 계기는 대조 체크리스트가 아니라 *"원본이 커진 걸 아는데 수량이 그대로네"* 라는 위화감 하나였다.

⚠️ **부분 수정에서 멈추지 마라.** 위 실사고에서 1차 수정(H1 레벨 추가)은 커버리지를 35%→53% 로만 올렸는데 수량이 늘었다는 사실만으로 "고쳤다"고 판단할 뻔했다. **버린 목록을 실제로 읽고 나서야** 남은 92개 절이 전부 Stage 2 리뷰 기록임이 보였고, 그때 2차 수정(H2·H3 에도 라운드 패턴 적용)으로 100% 가 됐다. **수량 증가는 수정의 증거가 아니다 — 잔여 목록이 비었는지가 증거다.**

#### 🔴 도메인 SSOT 경로 주입 (MANDATORY — 도메인 사실이 판정 재료가 되는 작업)

**적용 대상**: 코드 밖의 도메인 사실(외부 API 응답 구조·업무 규칙·회계/정산 정책·수집 제약 등)이
결함 판정의 재료가 되는 작업 전부. 스크래핑·ETL·결제/정산·외부 연동이 전형이다.

**규칙**: 프롬프트 주입이 가능한 리뷰어의 브리프에 **도메인 SSOT 파일 경로 표**를 포함하고, 다음
문장을 함께 넣는다.

> 도메인 사실의 SSOT 는 **코드 주석이 아니라 <카탈로그/스펙 경로>와 실측 자료**다. 도메인 전제를
> 근거로 결함을 주장하려면 그 파일을 **읽고 인용**하라. 코드 주석에서 도메인 규칙을 **추론**해
> 결함을 세우는 것은 근거로 인정되지 않는다.

**왜 필요한가 — 리뷰어의 독립성은 「모델이 다른 것」이 아니라 「재료가 다른 것」에서 나온다.**
코드만 받은 리뷰어는 코드 주석에서 도메인 규칙을 추론한다. 그 추론은 오케스트레이터의 추론과
**같은 재료에서 나오므로 독립적이지 않다.** 그런데 결과가 일치하면 오케스트레이터는 그것을
**「독립 확인」으로 읽는다** — 사각지대가 검증된 사실로 승격되는 순간이다. 리뷰어를 더 붙여도
전부 같은 재료를 보므로 이 형태의 오류는 **슬롯 수로 깨지지 않는다.**

**실사례 (2026-08-16 etl STAT-572 Phase 4 Stage 1)**: 오케스트레이터가 코드 주석 한 줄
(*"음수 허용: 초과보상 회수 행이 실재한다"* — **값의 부호**만 말하는 문장)에서 *"음수 행이 여러
회차에 분산된다"*(**행이 실리는 자리**)를 추론해 데이터 삭제 결함을 세웠고, `codex:critic` 이
**같은 주석**을 보고 **CRITICAL** 로 확인해 줬다. 실제로는 카탈로그 공식 문서 2건 + HAR 전수
43회차 실측이 그 전제를 정면으로 반증하고 있었고 **확인에 3분이 걸렸다**. 대가:
- 반증된 전제 위에 **잘못된 게이트**를 구현했고(그 게이트는 실사용 조건에서 **항상 거짓**이라
  본래 기능을 통째로 무력화했다), 다음 라운드에 다른 리뷰어가 그걸 다시 지적했다.
- 라운드 5·6·7 연속 non-APPROVE 를 **「발산형 정체」로 오판**했다. 발산이 아니라 **같은 사각지대를
  반복 관측**한 것이었고, 사용자가 도메인 사실 한 문장으로 즉시 깼다.

**MANDATORY — 3항 체크리스트**:
- [ ] 브리프에 **SSOT 경로 표**(파일/디렉토리 + 무엇이 들어 있는지)가 있는가?

      적으면 리뷰어가 정당하게 무시한다)

### Critic Deadlock 조기 감지 (공통 — canonical, MANDATORY)

**적용 대상**: 공통 Critic 실행 규칙이 적용되는 전 구간 — autopilot Phase 0/1, ralplan, team ralph. **Autopilot Phase 4는 예외** — `10-autopilot.md`의 자체 Deadlock 규칙(plugin native reviewer용)을 따른다.

**배경**: codex:critic은 `task --fresh` 호출이라 라운드 간 기억이 없다. 환경 invariant(예: 샌드박스 localhost 차단으로 "PG 미응답" 오인)나 이미 조정된 정책 이견(예: 위험 수용 방식)을 매 라운드 재발견해 **동일 finding을 영구 반복**할 수 있다. "양 Critic 무수정 APPROVE" consensus 요구는 이 시나리오에서 unworkable하므로, 조기 감지 + 근거 인용 자동 dismiss(ⓐⓑ)·사용자 결정(ⓒ)으로 라운드 낭비를 막는다. (2026-08-05 STAT-549 ralplan에서 codex critic이 동일 finding을 10회 반복하며 15라운드 한도를 소진한 실사례에서 도출. 당시 오케스트레이터가 자율 기각을 반복했는데, 본 규칙이 있었다면 3라운드째에 사용자 에스컬레이션으로 3~4라운드를 절약했을 것.)

**Deadlock 정의** — 다음 4조건 **모두** 충족 시:

1. 동일 Critic(주로 codex:critic)이 **연속 2라운드 이상** 비-APPROVE 판정 유지
2. 그 Critic의 핵심 finding이 의미상 **동일 영역**(동일 파일/절, 동일 우려 카테고리)에서 반복 — finding 표현이 oscillating해도 의미상 동일하면 인정
3. **다른 리뷰어**(Architect + 나머지 Critic)는 같은 시점에 APPROVE(조건부 포함) 안정 도달
4. finding의 성격이 다음 중 하나:
   - ⓐ **사용자 명시 환경 컨텍스트**가 finding의 전제를 무효화 (예: 샌드박스 DB 접근 불가 오인, 운영 DB 미가동)
   - ⓑ scope 기준 문서(PRD/spec) 대조 결과 **scope 밖**
   - ⓒ 사실이 아닌 **정책/취향 이견** (위험 수용 여부 등 — 실측으로 닫히지 않는 분쟁)

**MANDATORY — 매 라운드 양 Critic 판정 종합 직전 자체 검증 체크리스트 출력**:
- [ ] Critic별 연속 비-APPROVE 라운드 수: [OMC N=? / codex N=?] (N ≥ 2인 쪽 → 다음 항목, 없으면 본 규칙 미적용)
- [ ] 해당 Critic의 핵심 finding이 의미상 동일 영역 반복인가? (Y/N — 영역 명시)
- [ ] 다른 리뷰어들은 APPROVE 안정인가? (Y/N)
- [ ] 4-ⓐ/ⓑ/ⓒ 중 해당 있는가? (해당 항목 표기)
- [ ] **이 finding 이 이월 기록에 이미 있는가?** — `.omc/deferred/` · ralplan `ADR Follow-ups` 를 **동일 파일·동일 요지로 grep 대조**하고 결과를 적는다. 있으면 조건 1·2 가 자동 충족이다(과거 라운드에 이미 판단이 끝났다는 뜻). **이 대조 없이 "새 지적"으로 단정하지 말 것** — 대조를 빠뜨리면 이미 이월한 항목을 다시 고치게 된다(2026-08-08 실측: 이 대조로 round 2 ↔ round 10 재지적을 확정했다).
- [ ] 4항목 모두 Y → 다음 항목 (Deadlock 추정)
- [ ] **ⓐ/ⓑ 근거를 원문 인용 가능한가?** (ⓐ=사용자 발언·명시 환경 컨텍스트 문구 / ⓑ=scope 기준 문서 해당 절 — 인용문을 그대로 기재) → **Y = 자동 dismiss** (아래 「ⓐ/ⓑ 자동 dismiss」 — 질문·정지 없음) / **N 또는 ⓒ = 사용자 알림 + 선택 요청 후 정지** (근거 인용 없는 자율 dismiss·루프 강행 둘 다 금지)

**MANDATORY — ⓐ/ⓑ 자동 dismiss (2026-08-20 개정 — 멈춤 최소화)**: finding이 4-ⓐ 또는 4-ⓑ이고 그 근거를 **원문 그대로 인용**할 수 있으면(ⓐ=사용자 발언·명시 환경 컨텍스트 문구 / ⓑ=scope 기준 문서의 해당 절) 사용자 질문 없이 dismiss를 자동 적용한다. 아래 「옵션 A(dismiss) 처리」 전부(동일 요지 dismiss 유지·deferred 기록·조정 이력 주입)를 동일하게 수행하고, audit 표와 deferred 기록에 `자동 dismiss (ⓐ|ⓑ)` + **인용 근거 원문**을 명기한다. **근거를 문장으로 인용하지 못하면 자동 dismiss 불가** — 아래 에스컬레이션 보고로 폴백한다. ⓒ(정책·취향 이견)는 실측·문서로 닫히지 않으므로 항상 사용자 몫이다. (개정 근거: ⓐ는 사용자가 이미 말한 사실, ⓑ는 기준 문서에 이미 적힌 사실의 재확인이라 질문의 답이 정해져 있다. STAT-549에서 라운드를 태운 원인은 판단 오류가 아니라 기록·주입 누락이었고, 그 처리 장치는 그대로 유지된다.)

**MANDATORY — 사용자 에스컬레이션 보고 형식 (ⓒ 또는 근거 인용 불가 시)**:
1. **진단 요약**: 어느 Critic이 몇 라운드 연속 어떤 finding 영역을 반복하는지 1-2문장 + 4-ⓐ/ⓑ/ⓒ 분류
2. **다른 리뷰어 판정 현황** 1줄
3. **선택지 제시**:
   - 옵션 A: 해당 finding **명시 dismiss** → 남은 루프에서 dismiss 유지
   - 옵션 B: finding **수용** → 산출물 반영 후 루프 계속
   - 옵션 C: **루프 종료** → 현재 버전을 최종본으로 제시 (스킬별 산출물: ralplan=best version plan / Phase 0=spec / Phase 1=plan / team ralph=team-exec 결과)

**옵션 A(dismiss) 처리 — 사용자 선택 또는 ⓐ/ⓑ 자동 dismiss 시**:
- dismiss한 finding은 **동일 요지 기준으로 남은 루프 내내 dismiss 유지** (재차단·재질문 금지). 이후 라운드 post-call audit 표에 "dismiss 유지(사용자)"(자동 dismiss 건은 "dismiss 유지(자동 ⓐ|ⓑ)") 표기.
- ⚠️ **주입 불가 리뷰어의 dismiss 는 재지적이 구조적으로 확실하다** — 그 리뷰어에게는 dismiss 사실을 전달할 프롬프트 통로가 없기 때문이다(코드 주석 통로는 `10-autopilot.md` 「선제 리뷰 컨텍스트」가 보완하지만 보장은 아니다). 따라서 dismiss 직후 audit 표에 **"다음 라운드 재지적 예상"** 을 미리 표기하고, 실제 재지적이 오면 **놀라지 말고 즉시 "dismiss 유지"로 처리**한다(재질문·재수정 금지). 재지적을 새 finding 으로 세면 발산 판정의 입력값이 오염된다.
- `.omc/deferred/`에 기록 (finding 요지 + dismiss 사유 + 라운드 번호). 최초 1회만.
- **조정 이력 주입**: 이후 codex:critic 호출 프롬프트의 리뷰 대상 앞에 "오케스트레이터 조정 이력" 블록(사용자 dismiss된 finding 목록 + 사유 + "이 항목의 재지적은 판정에 반영되지 않는다" 명시)을 포함해, fresh 호출의 재발견이 판정을 오염시키지 않게 한다.

**잘못된 진행 금지 (anti-patterns, MANDATORY)**:
- ❌ 근거 원문 인용 없이 자율 판단으로 동일 finding을 기각하며 루프 지속 → **2회 반복 확인 시점에 본 규칙 적용** (ⓐ/ⓑ 인용 가능 = 자동 dismiss, 그 외 = 사용자 에스컬레이션) — 인용·기록·조정 이력 주입 없는 반복 기각이 STAT-549의 실패 형태다
- ❌ deadlock Critic을 루프에서 제외하고 나머지만으로 consensus 선언 → 사용자 선택 없이 금지
- ❌ dismiss 유지 중인 finding의 재등장을 사유로 수정 라운드 추가
- ❌ 사실 분쟁(실측으로 닫히는 것)을 본 규칙으로 dismiss → 사실 분쟁은 실행 검증으로 판정하는 것이 우선 (본 규칙은 ⓐⓑⓒ 한정)

### Finding 발산 조기 감지 (공통 — MANDATORY)

**적용 대상**: autopilot Phase 0/1, ralplan, team ralph **+ autopilot Phase 4 — `54-phase4-registry.md` 레지스트리의 전 행**(Stage 0·1·2 무관, 프롬프트 주입 가능 여부 무관, 리뷰어 종류 무관).

Deadlock(동일 finding **반복**)의 반대 패턴 — 리뷰어가 매 라운드 **새로운** finding을 내며 비-APPROVE를 유지해 라운드를 조용히 소진하는 경우를 잡는다. Deadlock은 "왜 반복하는가"라는 **원인**(주입 불가)으로 대상을 정하지만, 본 규칙은 **결과**(3라운드 연속 차단)로 정한다 — 원인별로 대상을 정하면 새로운 원인 조합이 나올 때마다 사각이 생기기 때문이다. (2026-08-07 실사고: `pr-review-toolkit`은 주입은 되는데 **이월이 안 되는** 새 조합이라 두 규칙 어디에도 안 걸렸고, 그 상태로 9라운드가 소진됐다.)

**발산 정의** — 다음 3조건 **모두** 충족 시:

   - **대상 축** — 차단 finding 이 매 라운드 **같은 파일군**에서 나오고, 그 파일군이 **산출물이 아니라 검증 장치**다(게이트·린터·검사 스크립트·그 회귀 등 "산출물을 지키려고 만든 코드"). **리뷰어가 매 라운드 달라도 성립한다.**

   - **라운드 축** — 리뷰어·파일군 **무관하게** 연속 **4라운드**(부분 재실행 회차 포함) 차단 등급 finding 이 ≥1건. 위 두 축이 **모두 비는 사각**을 막는다 — 리뷰어가 돌아가며 반려하고(리뷰어 축 미성립) 산출물이 프로덕션 코드일 때(대상 축은 검증 장치 한정) 발산이 규칙 밖으로 흐른다. **충족 시 — 자동 옵션 B 적용 + 사용자 보고, 질문 없이 계속 (2026-08-20 개정 — 멈춤 최소화)**. 자동화되는 것은 옵션 B 한 경로뿐이다 — 자율 '무기준 강행'(기준 기록 없는 계속)과 자율 '즉시 이월·종료'(옵션 A·C의 자동 선택)는 여전히 금지. (개정 근거: 2026-08-18 STAT-572 — 발화 4회 중 사용자 개입이 실제 종료를 만든 것은 정지 기준을 명시한 1회뿐이고 그 문안이 아래 기본 문안으로 이미 채택돼 있다. 답이 규칙 안에 있는 질문은 대기 비용만 남긴다. 옵션 B는 '계속'이라 아무것도 버리지 않으므로 발산 오판 시에도 비용이 라운드 수로 한정된다.):
- 옵션 A **(사용자 지시 시에만 — 자동 선택 금지)**: 현재 라운드 비차단 finding 전건을 Follow-ups/deferred에 기록하고 **이번 판정을 consensus로 처리** (계획/산출물 확정. **Phase 4에서는** 해당 리뷰어의 잔여 finding을 deferred에 기록하고 그 슬롯을 통과 처리 — audit 표에 "발산 규칙 사용자 결정"으로 표기)
- 옵션 B **(자동 기본값)**: 루프 계속 — 발산 충족 라운드에서 오케스트레이터가 **묻지 않고** 정지 기준을 audit 표와 deferred 에 기록하고 적용한다. **기록 없는 「계속」은 불가**(정지 기준 없이 계속하면 카운터만 리셋되고 같은 발산이 재현된다). 기본 문안: *"신규 실동작 결함(`10-autopilot.md` 「대상 축」 표의 동작 결함·증인 부재 ①·문면 ①)이 **2라운드 연속 0** 이면 잔여를 이월하고 통과"*. 사용자가 보고를 보고 다른 기준·옵션 A·옵션 C를 지시하면 그 지시가 즉시 우선한다. (2026-08-18 STAT-572: 발산 4회 발화 중 **8/14 R7 에서만** 사용자가 이 기준을 명시했고 그것이 실제 종료를 만들었다. 기준 없이 「계속」/「Stage 1 로」를 고른 나머지 3회는 카운터 리셋 → 같은 패턴 재현.)
  - **집행 (MANDATORY — 기준은 기록이 아니라 종료 장치다)**: 옵션 B 로 계속하는 동안 **매 라운드 판정 종합 직전에 기록된 정지 기준의 충족 여부를 체크리스트 1줄로 출력**한다 — `[ ] 정지 기준: <기록된 문안> — 충족 Y/N (근거 수치)`. **충족한 그 라운드에서 즉시 잔여 전건을 이월(Follow-ups/deferred)하고 통과(consensus) 처리한다.** 충족 후 「확인 라운드」·「최종 확인 라운드」류의 추가 라운드 개설 금지 — 통과 후 consensus 반영 수정이 `40-common-loop.md` 「공통 사소 수정 예외 규칙」 범위면 재루프 없이 마감하고, 그 범위를 넘는 본문 수정이 생긴 경우에만 그 수정에 한해 재루프한다. (2026-08-20 STAT-586 ralplan 실사고: R1 발화에서 옵션 B + 위 기본 문안을 기록했고 실동작 결함이 3→1→0→0 으로 **R4 에 기준 충족** — 종료 보고서에 "정지 기준 충족"이라고 스스로 적기까지 했다. 그런데 이월+통과 대신 확인 라운드 R5·최종 확인 R6 를 개설해 **~1.5h 를 더 태웠다**. 기준 기록 의무(2026-08-18)만으로는 안 멈춘다 — 충족 시점의 행동이 문장으로 적혀 있어야 멈춘다.)
- 옵션 C **(사용자 지시 시에만 — 자동 선택 금지)**: 루프 종료 — 현재 버전을 best version으로 제시

**보고 형식**: 어느 리뷰어가 몇 라운드째 어떤 새 영역들을 순차 지적했는지 **라운드별 1줄 나열** + 잔여 라운드 수 명시. Phase 4에서는 산출물 증감(줄 수)도 1줄 덧붙인다 — 지적이 느는 원인이 "산출물이 자라서"인지 "렌즈가 날카로워져서"인지 구분해야 개입(옵션 A/C 지시) 판단이 정확해진다.
- **같은 실행(Phase 4 1회·ralplan 1회) 안에서 2회째 이상 발화**면 보고 **첫 줄**에 「발산 누적 N회 · 첫 발화 이후 라운드 M · 이월 누적 K건」을 적는다 — 누적이 보여야 사용자가 개입(옵션 A/C 지시) 필요 여부를 판단할 수 있다. 매 발화를 「처음인 것처럼」 보고하면 누적이 가려진다. (2026-08-18 STAT-572: 4회 발화가 전부 첫 발화처럼 보고됐다.)

⚠️ **발산 조건이 충족될 때마다 매번 보고한다 — 질문은 하지 않는다.** 재발화 시에도 자동 옵션 B — 단 이미 기록된 정지 기준이 살아 있으면 새로 기록하지 않고 **그 기준의 카운트를 승계**한다(재발화를 이유로 카운터·기준 리셋 금지). 보고 생략도 금지 — 판단 근거(누적 라운드 수·finding 추이·산출물 증감·잔여 라운드)가 라운드마다 달라지므로, 사용자가 개입(옵션 A/C 지시)할 수 있으려면 매 발화가 보고돼야 한다. (Deadlock 의 dismiss 유지 규칙은 **개별 finding** 을 재차단하지 않는다는 것이고, 본 규칙의 보고 의무는 **루프 상태의 가시성**이다.)
