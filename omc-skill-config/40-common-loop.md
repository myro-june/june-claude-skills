### 공통 사소 수정 예외 규칙

autopilot Phase 0/1, team ralph, ralplan의 MANDATORY 루프 규칙에 한정된 예외. 다음 3종에 **명확히** 해당하는 경우에 한해 전체 루프 재실행 없이 바로 수정 가능:

1. **명백한 오타** — 의미/로직/사양 변경이 전혀 없는 단순 타이핑 실수
2. **포매팅** — 공백/들여쓰기/줄바꿈/마크다운 스타일 정리 (렌더링/의미 동일)
3. **주석/설명 오타** — 코드/사양/데이터 영향이 전혀 없는 텍스트 오타

**애매하면 묻지 않고 예외 미적용 — 전체 루프로 처리한다 (2026-08-20 개정 — 멈춤 최소화).** 다음 4종은 질문 대상이 아니라 **예외 비적용 확정** 사유다:
- 변수명/식별자 오타 (호출부 영향 가능)
- 숫자/데이터 값 변경 (의미 변경 가능)
- 문장 의미가 달라질 수 있는 오타
- 주석이지만 사양의 일부로 읽히는 문서성 텍스트

판단이 서지 않으면 사용자에게 묻는 대신 **예외 미적용(전체 루프)** 으로 처분하고 사유를 1줄 보고한다 — "<수정 요지> — <4종 중 해당 항목> 해당, 사소 예외 미적용·전체 루프로 재검토". 자의적 예외 적용 금지는 유지 — 본 개정은 애매를 '예외 아님'으로 자동 판정하는 것이지 예외 범위를 넓히는 것이 아니다. (개정 근거: 이 질문의 두 답 중 안전한 쪽은 항상 '루프 실행'이고, 질문이 아끼는 것은 루프 1회분인데 비용은 무기한 대기다.)

**MANDATORY — 예외 적용 시 자체 검증 체크리스트 출력**:
- [ ] 카테고리 명시: [1=명백한 오타 / 2=포매팅 / 3=주석/설명 오타]
- [ ] 변경 내용 1줄 요약 + 의미/로직 영향 없음 확인
- [ ] 위 "예외 비적용 확정" 4종(식별자 오타/숫자값/문장 의미/사양성 주석) 중 어느 하나에라도 해당하는가? (해당 시 예외 미적용 — 사유 1줄 보고 후 전체 루프로 처리. 사용자 질문·정지 없음)
- [ ] 동일 턴에 카테고리 외 변경(의미/로직 변경)이 1건이라도 섞이지 않았는가? (섞였으면 예외 무효 → 전체 변경을 루프 대상으로)

### 공통 작업 원칙 — scope 고정 + 최소 변경 (MANDATORY)

**적용 대상**: autopilot Phase 2(구현)·Phase 3(QA 수정), ralph/team ralph 수정 루프. (**autopilot Phase 4는 자체 규칙이 우선** — `10-autopilot.md`의 "scope 고정 및 finding 분류" + "수정 방식" 절. 본 절은 그 외 코드 작업 구간용.)

1. **scope 고정**: 크리티컬(보안 취약점, 데이터 손실/오염, 빌드·테스트 실패급)이 아닌 한, 이번 작업 범위를 벗어나는(Out of Scope) 발견·개선거리는 수정하지 않고 배제(dismiss)한다. 배제 항목은 `.omc/deferred/`에 기록만 한다 (`10-autopilot.md`의 "deferred 기록 파일 규격" 재사용). Scope Creep이 발생하지 않도록 현재 scope에만 집중한다.
   - scope 기준 문서: plan/spec 아티팩트 (autopilot은 Phase 4의 "scope 기준 문서 (우선순위)"와 동일, ralph/team ralph는 사용자 원 요청 + plan)
2. **원본 보존 + 단순성**: 원본 코드를 최대한 보존하고, 되도록이면 가장 간단하고 단순하지만 충분히 효과 좋은 방법으로 우선 진행한다. 동등 효과면 변경량이 적은 안을 택하고, 작업 사유와 무관한 리팩터링/개선을 같은 턴에 섞지 않는다.
3. **자매 파일·미러 레포 대칭 (MANDATORY)**: 쌍둥이 스크립트·미러 레포·대칭 문서가 있는 프로젝트에서는, 수정 **항목마다** "자매 쪽에 같은 형태가 있는가"를 확인하고 결과를 보고에 적는다 — `자매 확인: <위치> 동일 형태 있음→함께 수정 / 없음`. 한쪽만 고치면 같은 지적이 다음 라운드에 되돌아오고, 같은 변형이 한쪽 게이트만 뚫는다. (2026-08-07 실사례: etl 만 고치고 api 동형 코드를 안 옮겨 같은 지적이 3라운드 반복됐다. 이 체크를 위임 프롬프트에 넣은 라운드부터 반복이 끊겼다.)
   - **병렬 위임 시**: 자매 파일은 **같은 레인에 묶는다.** 레인을 나누는 축은 작업 종류가 아니라 **쓰기 대상 파일**이다 — 종류로 나누면 두 레인이 같은 파일을 열어 서로의 편집을 덮어쓴다.
   - **리뷰 측 재검증**: 이 자매 확인 보고는 autopilot Phase 4 **Stage 0 `change-impact-reviewer`** 가 행마다 직접 열어 재검증한다(`55-stage0-gate.md`). 오케스트레이터는 여기서 식별한 **자매 축을 Stage 0 호출에 선언**으로 넘긴다 — 구현자 지시만 있고 리뷰 슬롯이 없어 2026-08-14 결함이 4라운드 반복됐던 빈자리다.
   - **구조로 강제한다 (MANDATORY)**: 서술 요구만으로는 안 지켜진다. 전수 열거 진리표를 쓰는 작업이면 **「자매」를 표의 고정 열로 두고**, 행마다 `동일 형태 있음(위치) → 함께 수정` / `자매 없음(사유)` 중 하나를 채우게 한다. 빈 칸은 미완성으로 취급한다. **자매 축은 먼저 식별해 지시서에 적어 준다** — 실행자가 한쪽 계열만 훑고 "같은 기준으로 열거했다" 한 줄로 대체하는 것이 전형적 실패다. (2026-08-14 실사례: MSF↔RFM 미러 채널에서 MSF 7개 호출은 7행 표로 열거하고 RFM은 한 줄 서술로 넘어가, RFM 경계 1곳·자매 로더 계약 위반 1건이 다음 라운드 차단 결함이 됐다. 라운드 4·6·9·10에 같은 형태로 반복.)

4. **구현 스타일 — TDD 고전파 + 조회 쿼리 성능**: 정의는 `00-overrides.md` 「공통 구현 원칙 — 전역」이 SSOT — 여기 복제하지 말 것. 구현·수정을 위임하는 프롬프트, 특히 CLAUDE.md를 받지 않는 외부 엔진 워커(codex `task --fresh` 등)에는 그 요지(테스트 먼저·고전파 mock 경계·조회 쿼리 실행 계획 확인)를 명문 주입한다.

### 공통 — 뮤테이션 권한은 한 라운드에 한 레인만 (MANDATORY, canonical)

**적용 대상**: 병렬 레인이 **같은 작업 트리**를 공유하는 전 구간 — autopilot Phase 4 **Stage 0·1·2 포함**(본 절은 Phase 4 면제 대상이 아니다), ralph/team ralph 수정 루프, 검증 레인 병렬 위임.

뮤테이션 검증(지키려는 코드를 고의로 망가뜨려 테스트가 빨개지는지 보는 것)은 **작업 트리를 실제로 수정했다가 되돌리는** 행위다. 두 레인이 동시에 하면 한쪽의 원복이 다른 쪽의 뮤턴트를 지워 **죽었어야 할 뮤턴트가 살아 있는 것으로 보인다** — 「증인 없음」 오판을 만든다. 위 §6(대조군이 증인인지 확인)이 **하라고** 지시하는 행위의 **동시성 조건**이 이 절이다.

- **한 라운드에 뮤테이션 권한은 한 레인에만 준다.** 권한 레인을 위임 프롬프트에 명시하고, **나머지 레인에는 「뮤테이션 금지 · 전체 스위트 실행 금지」를 명문으로 넣는다** — 빠뜨리면 기본값이 "해도 된다"가 된다.
- 권한 없는 레인은 **정적 검증만** 쓴다(grep · 코드 독해 · 타입 추론 · 파일 대조). 실행이 필요한 finding 은 **「판정 불가 — 실행 검증 필요」** 로 분리하고 **무엇을 돌리면 판정되는지** 적게 한다. 판정 불가는 차단 등급으로 올리지 않는다.
- **타입 레벨 프로브는 면제**다 — 러너가 트랜스파일만 하고 타입을 무시하는 구성(vitest+SWC 등)에서는 타입 프로브가 다른 레인의 실행 결과에 간섭하지 않는다. 면제 근거는 **러너 구성**이지 프로브 종류가 아니므로, 러너가 타입체크를 겸하면 면제도 사라진다.

⚠️ **이 충돌은 흔적이 안 남는다.** 일반 편집 충돌은 diff 에 보이지만 뮤테이션 충돌은 원복돼 사라지고 **「테스트가 이상하게 널뛴다」** 로만 나타난다. 사후 원인 규명이 사실상 불가능하고, **그 라운드의 증인 판정 전체를 못 믿게 된다** — 손실 단위가 finding 1건이 아니라 라운드 1회다.

> **실사고 (etl STAT-572 Phase 4)**: 두 레인이 같은 트리에서 병렬로 뮤테이션을 돌려 같은 스위트가 연속 4회 `36 / 0 / 1 / 5 failed` 로 널뛰었다. 어느 회차가 참인지 사후 판별이 불가능했다.

### 공통 — 서브에이전트 산출물 회수 규율 (MANDATORY, canonical)

**적용 대상**: 서브에이전트에게 산출물(리뷰 보고서·분석 결과·작업 보고 등)을 받는 **전 구간** — autopilot Phase 0/1/**4**, ralplan, ralph, team ralph.

서브에이전트가 **완료 신호만 보내고 산출물 본문이 도착하지 않는** 사례가 반복 관측됐다(2026-08-07: 6슬롯 중 5건이 재요청을 요구했고, 한 슬롯은 에이전트 3개·시도 7회를 소모했다). 회수하지 못한 산출물을 APPROVE·통과로 카운트하는 것은 금지이므로, 아래 사다리를 순서대로 적용한다.

1. **1차 재요청** — "**이 메시지에 대한 답장 본문으로** 전문을 보내라(요약 말고)"를 명시. 회수에 성공한 사례는 전부 이 문구를 포함했다.
2. **2차 파일 채널** — 산출 경로를 지정해 파일로 쓰게 하고 응답은 한 줄만 받는다(`WROTE <path> — <요약 수치>`). 쓰기 허용 범위를 **스크래치패드로 한정**하고 대상 레포 수정 금지를 함께 명시한다.
3. **3차 신규 재호출** — 위가 실패하면 새 에이전트로 재호출한다.

- **같은 슬롯에서 2차까지 실패하면 "요청 방식"이 아니라 "전달 경로"를 의심한다.** 다른 슬롯이 같은 방식으로 성공했다면 방식은 변수가 아니다.
- **예방(권장)**: 최초 호출부터 산출 경로를 지정해 **파일 산출을 기본**으로 두면 사다리가 거의 발동하지 않는다.
- ⚠️ **회수 요청에 새 과제를 얹지 말 것.** 회수는 **이미 생성된 산출물의 전달만** 요구한다. 추가 질문·교차 검증·후속 수정 지시는 회수 완료 후 **별도 메시지**로 분리한다 — 과제를 얹으면 옮겨 적기가 재작업으로 바뀌어 또 idle 로 끝난다(요청에 과제를 얹은 슬롯만 회수에 실패한 실측이 있다).

#### 최초 위임 프롬프트에 **넣어 두면 사다리가 안 발동하는 4줄** (2026-08-15 실측)

한 세션에서 `idle_notification` 만 오고 본문이 없는 사례가 **10회 이상** 났다. 원인은 두 가지이고 둘 다 **선제 문구로 예방된다**:

1. 에이전트가 **plain text 로만 출력**하고 전달 도구를 안 부른다 — 서브에이전트의 본문 출력은 오케스트레이터에게 **전달되지 않는다**.
2. 오케스트레이터형 서브에이전트가 **손자 스폰에 실패**하고도 "스폰 완료"를 결과로 착각한다.

→ 최초 프롬프트 말미에 아래를 **항상** 넣는다:

> **보고**: 결과를 **이 대화의 본문으로** 전달 도구(`SendMessage` 등)를 통해 보내라 — plain text 출력은 전달되지 않는다. 파일에 쓰지도 마라.
> "완료했습니다" 류 **요약은 무효**다. 본문 전건이 필요하다.
> finding **0건이면 0건이라고 명시하고 무엇을 어떻게 확인했는지** 적어라 — "0건"만 오면 회수 실패로 처리한다.
> (손자 에이전트를 스폰한다면) **`name` 파라미터를 넘기지 마라** — `Teammate 는 다른 teammate 를 스폰할 수 없다 — team roster is flat` 으로 실패한다.

- **0건 안내가 왜 필요한가**: 0건이 정상인 슬롯(security 등)은 "없음"만 보내고 끝내기 쉽다. 그러면 **미회수와 구분되지 않아** APPROVE 로 셀 수 없다.
- ⚠️ **`idle_notification` 이 오면 본문이 함께 왔는지 먼저 확인하라.** 없으면 즉시 회수 — idle 은 "끝났다"이지 "보고했다"가 아니다.

#### 지시 이탈을 **막지 말고 근거를 요구**한다 (2026-08-15 실측)

위임 프롬프트의 처방이 틀릴 수 있다. 5레인 웨이브에서 **5레인 전부가 오케스트레이터 지시를 벗어났고 다섯 번 다 근거가 더 나았다**(자매 선례를 형태만 보고 복사하면 나빠지는 경우 · 처방이 다른 방어를 끄는 경우 · 개명 대신 제거가 강한 경우 등). 그래서 프롬프트에 아래를 넣는다:

> 이 처방이 틀렸다고 판단되면 **다르게 하되 근거를 보고에 명시하라.** 기계적 집행보다 근거 있는 이탈이 낫다. 단 **scope 는 벗어나지 마라** — 처방의 *형태*는 바꿔도 *대상*은 그대로다.

**scope 단서가 핵심이다** — 이탈 허용이 범위 확대 허가가 되면 안 된다.

#### 🔴 **문법 형태를 센 자매 대칭 주장은 원인 축을 직접 확인한다** (2026-08-15 실측)

리뷰어가 **같은 코드 형태의 occurrence 수**로 "자매 대칭이니 전부 고쳐야 한다"를 주장하면, 오케스트레이터는 **그 형태가 실제로 같은 원인에서 오는지** 재현한다. 형태가 같다고 **위험 구조가 같지는 않다.**

**실사례**: 리뷰어 2명이 `err: error` **47 occurrence / 19파일**을 세어 *"MSF·RFM 자매 완전 대칭 누출, 전역 sanitizer 필요"*로 Critical 을 냈다. 오케스트레이터가 프로브로 재현하니 **자격증명 누출은 `apiRequestContext` 한 API 에서만** 발생했다:

| 오류를 만든 API | 첫 줄 | cookie/토큰 |
|---|---|---|
| `apiRequestContext.*` | `apiRequestContext.post: connect ECONNREFUSED …` (11줄) | 🔴 실림 |
| `page.evaluate` (in-page fetch) | `page.evaluate: TypeError: Failed to fetch` (4줄) | ✅ 없음 |
| `page.goto` | `page.goto: net::ERR_… at http://…` (4줄) | ✅ 없음 |

→ 실제 누출면은 **1곳**이었다. 47곳 리팩터가 프로브 20줄로 1곳이 됐다.
**두 리뷰어 모두 `err: error` 라는 문법 형태를 셌고, 아무도 그 `error` 가 어느 API 에서 왔는지 묻지 않았다.**

**규칙**: *"N곳이 같은 결함이다"* 형태의 지적은 **N 을 세는 축**과 **결함을 만드는 축**이 같은지 확인한 뒤에만 채택한다. 다르면 결함 축으로 다시 센다.
(같은 세션의 자매 사례 — *"인터페이스를 한 번만 선언하고 재사용해서 교차 대입이 된다"* 는 근거도 틀렸다. 실제로는 **따로 선언해도 구조적 타이핑으로 대입된다** — 결론은 옳고 근거만 틀렸다. 근거가 틀리면 **처방 범위가 틀어진다.**)

### 공통 — 위험 명령의 인자는 파생하지 말고 조립한다 (MANDATORY, canonical)

**적용 대상**: 파괴적·비가역 명령(DB migration·배포·삭제·덮어쓰기)의 대상을 지정하는 **전 구간**. 오케스트레이터 자신에게도 적용된다.

1. **파생 금지** — 위험한 값(운영 DB URL, 운영 배포 대상, 실제 삭제 경로)에서 출발해 **치환으로** 안전한 값을 만들지 않는다. 치환이 실패하면 **원본이 그대로 남으므로 fail-open** 이다. "위험한 것에서 시작해 고쳐 쓰기"가 구조적 결함이다.
2. **조립** — 안전한 값을 조각에서 **새로 만든다**. 조각이 빠지면 결과가 대놓고 망가져 **실패가 눈에 보인다**.
3. **치환이 불가피하면 결과를 먼저 출력해 확인한다** — `sed`·`awk`·`jq`·`tr` 은 매칭 실패 시 **에러 없이 원본을 반환**한다. BSD/GNU 방언 차이(`-E`·`\b`·`$` 앵커·`-i` 인자)가 흔한 원인이다. `echo "$결과값"` 한 줄이 유일한 방어선이다.
4. **fail-closed 가드** — 파괴적 명령 **앞에** 대상이 안전한지 검사하는 게이트를 둔다. **허용 목록(allowlist)** 으로 만든다 — 목록에 없는 대상은 거부. 금지 목록(denylist)은 새 공유 자원이 생길 때 자동으로 뚫린다.
5. **물리 분리 우선** — 이름만 다른 같은 서버가 아니라 **다른 포트·다른 인스턴스·일회용 컨테이너**를 쓴다. 옆 자원이 아예 없으면 실수해도 닿을 대상이 없다.
6. **손댈 필요를 없앤다** — 위 1~5 를 매번 사람·에이전트가 지키게 하는 대신, 준비·검증·정리를 한 명령으로 묶어 **인자를 만질 일 자체를 제거**한다. 이번 사고는 "조심하지 않아서"가 아니라 **"조심해야 할 일을 시켜서"** 났다.

### 공통 — 검증되지 않은 단언을 만들지 않는다 (MANDATORY, canonical)

**적용 대상**: **모든 산출물** — 코드·주석·문서·**커밋 메시지**·PR 설명·**서브에이전트 위임 프롬프트**·**사용자 보고**·`.omc/deferred/` 기록. 전 구간(autopilot 전 Phase · ralph · team ralph · ralplan)이며 **오케스트레이터 자신에게도 적용된다.**

이 절은 바로 위 「에이전트 자기보고는 주장이지 사실이 아니다」의 **반대편**이다 — 그쪽이 **받는** 규율이라면 이쪽은 **만드는** 규율이다.

**산출물마다 무게가 다르다**:
- **문서·주석·커밋 메시지** → 나중에 검증된다. 거짓이면 **새 finding** 이 되어 라운드를 태운다. 코드는 테스트가 지켜주지만 **문면의 사실 주장은 아무도 지켜주지 않는다**(`check-agents-md-drift` 류 게이트도 카운트 패턴만 본다. 커밋 메시지는 어떤 게이트도 안 본다).
- **위임 프롬프트·보고** → **즉시 다른 참여자의 전제가 된다.** 거짓이면 그 위에 작업이 쌓이므로 되돌리는 비용이 훨씬 크다.

**판단 기준 (이 절의 핵심 — 나머지는 전부 이것의 적용이다)**:

> **이 문장을 테스트로 바꿀 수 있는가?**
> - **바꿀 수 있다 → 테스트로 옮기고 문장은 지운다.**
> - **바꿀 수 없다 → 그것은 의도·이유·트레이드오프다. 그것만 문장으로 남긴다.**

같은 사실이라도 **문장에 적으면 부채**(시간이 지나면 반드시 틀린다)고 **테스트에 적으면 자산**(코드가 바뀌면 테스트가 알려 준다)이다. ⚠️ **"정확하게 적기"로는 수렴하지 않는다** — 범위·시점·근거를 덧붙여 정확도를 올리면 **적을 문장이 늘고 그 부속물이 또 검증 대상이 된다.** 수렴하는 유일한 방향은 **문장을 줄이고 테스트로 옮기는 것**이다.

1. **개수·목록을 복제하지 않는다** — `N곳`·`N종`·`N건`. 세는 대상이 늘면 즉시 거짓이 된다. **SSOT 를 가리키기만 한다.** 수치가 판정에 필요하면 문장이 아니라 **assert 로 고정**하고, 사람에게 보여야 하면 **실행 출력을 인용**한다(그 자리에서 세어 넣지 않는다).
2. **검증 가능한 사실은 문장이 아니라 테스트에 적는다** — *"실측 0건"* · *"양 레포에 있다"* 류는 쓰는 순간 부채다. 같은 사실을 **대조군 케이스**로 고정하면 자산이 된다(2026-08-08 실측: *"`keyword_count` 는 두 레포에 실제로 있는 이름"* 이라는 주석이 거짓이 됐는데, **과차단 방지 케이스 1건이면 문장 자체가 불필요**했다). 테스트로 고정할 수 없는 사실이면 **적지 않는 쪽이 기본**이고, 그래도 남겨야 하면 범위·시점을 붙여 **유효기간이 있는 관찰**임을 드러낸다.
3. **인과는 대조군이 있을 때만 적는다** — *"X 때문에 통과한다"* 는 **X 를 죽였을 때 판정이 뒤집히는 회귀가 있을 때만** 쓴다. 대조군을 만들 수 없으면 **인과를 적지 않는다** — 검증되지 않은 인과는 다음 라운드에 반드시 재검토 대상이 된다(2026-08-08 실측: 과차단 대조군 주석이 단언한 인과가 실측과 **반대**였다).
4. **열거를 유지하는 문서가 있으면, 열거 대상을 새로 만들 때 같은 커밋에서 갱신한다** — 회수 목록·소비자 목록·앵커 목록. 새 항목을 만들고 목록을 안 고치면 **그 순간 목록이 거짓이 된다.** ⚠️ 이 형태는 **diff 에 안 보이므로 리뷰로 잡히지 않는다**(목록 줄은 안 바뀌었으니까). 나머지 넷이 *"틀린 걸 적었다"* 라면 이것은 *"참을 거짓으로 만들었다"* 다.
5. **"무엇"은 산출물에 맡기고 "왜"만 적는다** — 코드를 읽으면 아는 사실을 재서술하지 않는다. **재서술본은 한 세대 뒤처진다.**
6. **대조군을 추가했으면 그것이 증인인지 확인한다** — 지키려는 코드를 죽였을 때 그 케이스가 **단독으로** 죽어야 한다. 안 죽으면 그 케이스는 **초록불만 늘린 것**이다. ⚠️ 위 3번이 *"주석에 인과를 쓸 때"* 의 조건이라면 이것은 *"테스트를 쓸 때"* 의 조건이다 — **주석을 한 줄도 안 써도 이 공백은 생긴다.** 그리고 **초록불이 이 공백을 가린다**: 케이스가 전건 통과하니 잘 덮여 있다고 느끼는데, 실제로는 지키려던 계약에 증인이 0명일 수 있다. 망가뜨려 봐야만 보인다. (2026-08-10 실측 2건 — ⓐ 게이트가 *"`src/` 의 모든 파일을 훑는다"* 를 계약으로 못박았는데 스캔을 `.ts` 로 좁힌 mutant 가 회귀 **74건 전건을 그대로 통과**했다(fixture 가 전부 `.ts` 라서다). ⓑ 같은 라운드에 새로 쓴 주석의 인과가 mutant 생존으로 드러나 그 문장을 걷어냈다.)

7. **보호·탐지 장치의 발화 조건은 「코드가 읽는 변수」로 적는다** — 시나리오 이름으로 적지 않는다. *"전체 리셋은 잡는다"* 처럼 **상황의 이름**으로 적으면, 그 이름이 코드의 판정 재료가 아닐 때 **같은 문단 안에서 자기모순**이 된다(그 시나리오의 일부가 바로 아래 미탐지 목록에도 들어간다). 판정 함수가 실제로 읽는 재료를 그대로 옮겨 적으면 미탐지 목록은 **저절로** 배타적이 된다.
   - ⚠️ **범위를 좁히는 것만으로는 안 고쳐진다.** 틀린 축 위에서 좁히면 **더 정밀한 거짓**이 될 뿐이다. 고칠 대상은 넓이가 아니라 **축**이다.
   - ⚠️ **처방은 「코드를 늘려 문장을 참으로 만드는 것」이 아니라 「문장을 판정 재료로 다시 쓰는 것」이다.** 게이트 라운드에서 미적용 경로를 채우는 것은 scope 확대이고, 새로 쓴 코드가 또 검증 대상이 되어 라운드를 늘린다. 못 닫은 경로는 **「알려진 한계」로 적고 후속으로 넘긴다.**
   - (2026-08-15 etl STAT-572 실사례 — **같은 뿌리로 2세대**: Wave 9 는 탐지를 한 갈래에만 넣고 문면은 전 경로를 말했고, 이를 고친 Wave 10 은 주장을 좁히면서 축을 `reset 범위` 로 잡았다. 실제 발화 재료는 `marker 구성 + 해당 구간 행 수` 였으므로 *"전체 reset 은 잡는다"* 와 미탐지 ①이 겹쳐 자기모순이 됐다. 두 세대 모두 **독립 리뷰어가 차단**했다.)

- ⓐ **테스트로 옮길 수 있는가?** → 옮기고 **문장은 지운다**.
- ⓑ 못 옮긴다면 **이 문장이 없으면 무엇을 못 하는가?** → 답이 안 나오면 **지운다**.
- ⓒ 그래도 남긴다면 **직접 확인했고** 범위·시점이 붙어 있는가? → 아니면 **지운다**.
- ⓓ **발화 조건을 적었다면 그것이 판정 함수가 읽는 변수인가?** → 시나리오 이름이면 **판정 재료로 바꿔 쓴다**(§7). 바꿔 쓴 뒤 **미탐지 목록과 겹치는지** 확인한다 — 겹치면 축이 아직 틀린 것이다.
